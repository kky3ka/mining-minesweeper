# 採掘マインスイーパー・ローグライト 企画書

## 1. 企画概要

### コンセプト

マインスイーパーのルールをベースにした、ドット絵のブラウザ向け採掘ローグライトゲーム。

プレイヤーはダンジョンを探索し、数字から周囲の「宝」と「地雷」の存在を推測しながら採掘する。スタミナを管理しつつ階段を見つけ、さらに深く進むか、戦利品を持って帰還するかを判断する。

探索に失敗しても、失ったアイテムはそのフロアに残り、再挑戦や他プレイヤーによる非同期救助で回収できる。

### 対応環境

- Webブラウザ
- PC / スマートフォン対応
- フロントエンド：TypeScript + Phaser + Vite を想定
- 本番環境は静的ファイル中心の構成を想定
- セーブ・引き継ぎ等のAPIはPHPを利用する想定

---

## 2. 基本ゲームループ

```text
拠点
 ↓
ダンジョンを選択
 ↓
ダンジョンへ出発
 ↓
フロアを探索・採掘
 ↓
宝や地雷を発見
 ↓
階段を発見
 ↓
「帰還する？」を選択
 ├─ 帰還 → 拠点へ
 └─ 進む → 次のフロアへ
             ↓
          最深部へ
             ↓
        大宝を獲得
             ↓
        自動的に帰還
             ↓
          ダンジョンクリア
```

---

## 3. 探索システム

### フロア

- ダンジョンは複数のフロアで構成される。
- 各フロアは自動生成。
- マップは広めのグリッドで構成する。
- 画面に全体を収めず、スクロールして探索する。
- 初期案では **30×30マス**を想定。
- 未探索部分は隠される。
- マップの内容は生成時点で確定する。
- 失敗した場合は、同じマップ・フロアを再挑戦できる。

### 開始地点

- 各フロアで、ゲーム側が最初に掘れるマスをランダムに決定する。
- プレイヤー自身が開始地点を選ぶことはできない。
- 開始地点から8方向へ掘ることができる。

### 操作

- 上下左右＋斜めの **8方向**へ掘れる。
- スマートフォンでのタップ操作を考慮した設計。
- キャラクターの具体的な移動・採掘アニメーションは後で決定する。

---

## 4. マインスイーパー要素

### 数字

各マスに表示される数字は、そのマスの周囲8マスに存在する、

- 宝
- 地雷

の合計数を表す。

例：

```text
周囲8マスに
宝1個 + 地雷1個
↓
数字は「2」
```

### 数字の固定

- 数字はマップ生成時に決定。
- 宝や地雷を掘り出しても数字は変化しない。
- 地雷を掘った後も、周囲の数字はそのまま。

### 0マス

- 周囲8マスに宝・地雷が存在しない場合は「0」。
- 0マスを掘ると、周囲の安全なマスを自動的に開示する。
- 階段は0マスの中からランダムに配置される。

### 採掘前の情報

- 掘る前に、そのマスを掘るために必要なスタミナを確認できる。
- 実際に何があるかは、掘るまで分からない。
- 「どこを掘るか」だけでなく「そのマスにスタミナを使う価値があるか」も判断材料になる。

---

## 5. スタミナ

スタミナを探索中の主要リソースとする。

### 基本ルール

- ダンジョン突入時はスタミナ最大。
- 採掘するとスタミナを消費。
- 地雷を掘るとスタミナにダメージを受ける。
- スタミナが0になると探索失敗。
- HPは設定せず、スタミナだけで管理する。

### 地雷

- 初期バージョンでは地雷は1種類。
- 地雷を掘るとスタミナダメージを受ける。
- ダメージ量はプレイテストで調整する。
- 掘り出した地雷は処理済みとなり、同じマスを再び掘ることはできない。
- 地雷を掘っても周囲の数字は変化しない。

---

## 6. フロア進行・マップ生成

### マップ

- 広めのグリッドマップを自動生成する。
- 初期案は30×30マス。
- 画面内に収まらないためスクロールして探索する。
- 未探索部分は隠される。
- マップの内容自体は生成時点で確定する。
- 失敗後も同じマップを再利用できる。

### 開始地点

- ゲーム側がランダムにプレイヤーの開始地点を決定する。開始地点は隣接する地雷・宝物数が0のマスである。
- 開始地点から8方向に掘れる。

### 階段

- 階段は0マスの中からランダムに配置する。
- 階段の位置が開始地点から到達可能かどうかは、マップ生成時には検証しない。

### フロア踏破

階段を発見すると、

> 「帰還する？」

という選択を行う。

- **帰還**：その時点の戦利品を持って拠点へ戻る。
- **進む**：次のフロアへ移動する。

階段を見つけた後も、同じフロアでの探索を続けることが出来る。

これにより、各フロアで

> 「ここまでの戦利品を持って帰るか、さらに深く潜って稼ぐか」

というリスク・リターンの判断が発生する。

### 最深部

- ダンジョンの最深部には、そのダンジョン固有の「大宝」が存在する。
- 大宝を取得すると、その場で自動的に拠点へ帰還する。
- 大宝の取得をもってダンジョンクリアとする。
- 大宝は通常アイテムとは扱わず、売却対象にもならない。
- 大宝取得時は自動帰還するため、大宝を失うことはない。

---

## 7. アイテム

### 通常宝物アイテム

ダンジョン内で入手できる一般的な資源。

例：

- 鉄
- 銅
- 銀
- 金

売却してお金にできる。

### レア宝物アイテム

低確率で入手できる特殊アイテム。

例：

- 古代コイン
- 遺物
- レアな宝石

売却してお金にできるほか、アイテム図鑑に記録される。

### 装備アイテム

- 探索時に持ち込むことが出来るアイテム。探索失敗時に **50%** 失う。

### 大宝

- 各ダンジョン固有。
- 最深部に存在。
- 入手すると自動帰還。
- ダンジョンクリア条件。
- 通常アイテムとは別扱い。

### アイテム図鑑

入手した通常・レアアイテムを記録する。

収集・コンプリート要素として利用する。

## 8. 永続成長

ダンジョンから帰還して得た資金などを利用し、キャラクターを恒久的に強化する。

現在想定している成長要素は3種類。

### 最大スタミナ

- 探索できる量が増える。
- より深いフロアを目指しやすくなる。

### 採掘力

- 採掘に必要なスタミナコストを軽減する方向で機能させる。
- 正確な計算式は未決定。

### アイテム容量

- 探索中に持ち帰れるアイテム量を増やす。
- スロット個数制

### 装備量

- 探索時に持ち歩けるアイテム枠を増やす。

---

## 9. 探索失敗とアイテムドロップ

### 失敗条件

- スタミナが0になると探索失敗。

### アイテムの損失

探索失敗時、所持していたアイテムの **50%**　と今回の探索で得た宝物を失う。

ただし、アイテムそのものが消滅するわけではない。

### ドロップ地点

- 失ったアイテムは、失敗した時点の同じフロアに残される。
- 後の探索で発見・回収できる。
- 回収したアイテムは通常の所持アイテムへ戻る。

50%の端数処理方法は未決定。

---

## 10. 非同期救助

他プレイヤーによる非同期型の救助システムを導入する。

### 基本構造

```text
探索失敗
 ↓
アイテム50%を失う
 ↓
同じフロアにアイテムが残る
 ↓
自分で再挑戦して回収
       または
他プレイヤーに救助してもらう
```

### 救助報酬

- 救助されたプレイヤーの失ったアイテムは、そのまま元のプレイヤーへ返す。
- 救助したプレイヤーには別途報酬を与える。
- 救助報酬は元プレイヤーのアイテムから差し引く方式ではなく、別途生成する想定。

救助の制限時間・報酬量・救助UIなどは未決定。

## 11. ダンジョン

プレイヤーは複数のダンジョンから探索先を選択する。

各ダンジョンは以下のデータを持つ。

- ダンジョン名
- 入手可能アイテム
- フロア数
- 大宝
- マップチップ / ビジュアルデザイン
- 必要に応じた難易度設定

ゲームシステム自体は共通化し、新しいダンジョンはデータやアセットを追加することで拡張できる構成を目指す。

### ダンジョン例

#### 鉱山

- 岩・土系のマップ
- 鉄、銅、銀、金など
- 大宝：巨大な金塊など

#### 古代遺跡

- 石造りの遺跡系マップ
- 古代コイン、遺物、宝石など
- 大宝：王家の秘宝など

※上記はイメージ例であり、正式な内容は未決定。

## ダンジョン・探索エリアデータ設計

### 概要

ダンジョンに関する設定は、ゲームロジックと分離したデータとして管理する。

現在はJSONファイルで管理し、将来的にPHP API + SQLデータベースへ移行できる構造を想定する。

ダンジョンは複数の「探索エリア」から構成される。

```text
ダンジョン
 ├─ 基本情報
 ├─ 大宝
 └─ 探索エリア
      ├─ 進入条件
      ├─ クリア条件
      ├─ マップ設定
      └─ アイテム出現設定
```

---

### ダンジョンデータ

ダンジョンには以下の情報を持たせる。

| 項目              | 内容                     |
| --------------- | ---------------------- |
| `id`            | ダンジョンを一意に識別するID        |
| `name`          | ダンジョン名                 |
| `largeTreasure` | ダンジョン最深部で獲得する大宝のアイテムID |
| `stages`        | 探索エリアの一覧               |

#### 例

```json
{
  "id": "old_mine",
  "name": "廃鉱山",
  "largeTreasure": "golden_nugget",
  "stages": []
}
```

---

### 探索エリア

ダンジョン内の各エリアは `stages` として管理する。

探索エリアには以下の情報を持たせる。

| 項目               | 内容                 |
| ---------------- | ------------------ |
| `id`             | 探索エリアを一意に識別するID    |
| `sequence`       | ダンジョン内での進行順        |
| `name`           | プレイヤーに表示する探索エリア名   |
| `entryCondition` | エリアへの進入条件          |
| `clearCondition` | エリアのクリア条件          |
| `map`            | マップに関する設定          |
| `items`          | その探索エリアで掘れるアイテムの一覧 |

探索エリアの名称は「1階」「2階」のような階層名に限定しない。

例えば、

* 坑道入口
* 第一採掘場
* ハートの間
* スペードの部屋
* 地下湖
* 王家の地下室

など、ダンジョンの世界観に合わせた名称を設定できる。

`sequence` はゲーム内部での進行順を管理するために使用し、表示名とは分離する。

---

### エリア進入条件

各探索エリアには `entryCondition` を設定できる。

進入条件によって、プレイヤーがそのエリアを探索できるかを判定する。

基本的には条件を持たないエリアを最初の探索エリアとし、後続エリアでは前のエリアのクリアなどを条件として設定できる。

#### 例

```json
"entryCondition": {
  "type": "previous_stage_clear"
}
```

この場合、直前の探索エリアをクリアすると進入可能になる。

将来的には以下のような条件を追加できる。

```text
previous_stage_clear
item_required
item_count_required
money_required
upgrade_level_required
large_treasure_required
```

条件を複数組み合わせる場合も想定する。

例えば、

```json
"entryCondition": {
  "type": "item_required",
  "itemId": "ancient_key"
}
```

のようにする。

複数条件については、将来的に `all` / `any` などの条件グループを追加することで対応する。

---

### エリアクリア条件

各探索エリアには `clearCondition` を設定する。

エリアクリア後は次の探索エリアへの進入や、帰還などのゲーム進行が可能になる。

#### 階段発見によるクリア

現在の基本ルールでは、探索中に階段を発見すると、その探索エリアを「踏破済み」とする。

```json
"clearCondition": {
  "type": "find_stairs"
}
```

階段を発見した後、プレイヤーは以下を選択できる。

* 現在のエリアをさらに探索する
* 次の探索エリアへ進む
* 拠点へ帰還する

このため、「階段発見」は探索エリアのクリア条件であると同時に、安全に帰還・進行できるチェックポイントとして扱う。

---

### 将来的なクリア条件

クリア条件は `type` によって種類を切り替えられるようにする。

想定する条件：

```text
find_stairs
find_large_treasure
collect_item
explore_percentage
defeat_boss
special_condition
```

例えば特定アイテムの取得を条件とする場合、

```json
"clearCondition": {
  "type": "collect_item",
  "itemId": "ancient_key"
}
```

マップの一定割合を探索する場合、

```json
"clearCondition": {
  "type": "explore_percentage",
  "value": 80
}
```

などとする。

ただし、実際に使用するクリア条件はゲーム仕様の決定に合わせて追加する。

---

### マップ設定

各探索エリアは、固定マップまたはランダムマップのどちらかを使用できる。

```json
"map": {
  "type": "random",
  "width": 30,
  "height": 30,
  "mineProbability": 5,
  "treasureProbability": 3
}
```

#### マップ設定項目

| 項目       | 内容                   |
| -------- | -------------------- |
| `type`   | `random` または `fixed` |
| `width`  | マップの横幅               |
| `height` | マップの縦幅               |
| `mapId`  | 固定マップを使用する場合のマップID   |
| `mineProbability` | マップ全体に対する地雷の配置率（％） |
| `treasureProbability` | マップ全体に対する宝物の配置率（％） |

#### ランダムマップ

```json
"map": {
  "type": "random",
  "width": 30,
  "height": 30,
  "mineProbability": 5,
  "treasureProbability": 3
}
```

ゲーム開始時などにマップを自動生成する。

同じ探索エリアでも、プレイするたびに異なるマップを生成できる。

#### 固定マップ

```json
"map": {
  "type": "fixed",
  "width": 25,
  "height": 25,
  "mineProbability": 10,
  "treasureProbability": 3,
  "mapId": "old_mine_collapse"
}
```

固定マップでは、別途管理されたマップデータを `mapId` で参照する。

固定マップは、

* 特殊な地形
* 一本道
* 特定位置に配置されたギミック
* ストーリー上の重要地点
* 特殊な大部屋

などに利用する。

同一ダンジョン内で固定マップとランダムマップを混在させることができる。

---

### アイテム出現設定

各探索エリアで掘れるアイテムは `items` に登録する。

```json
"items": [
  {
    "itemId": "copper_ore",
    "probability": 50
  },
  {
    "itemId": "iron_ore",
    "probability": 35
  },
  {
    "itemId": "silver_ore",
    "probability": 15
  }
]
```

| 項目            | 内容             |
| ------------- | -------------- |
| `itemId`      | アイテムマスターデータのID |
| `probability` | その探索エリアでの出現確率(%)  |

`itemId` はアイテム名そのものではなく、アイテムデータを参照するIDとする。

アイテムの名前、売却価格、種類などの情報はアイテムデータ側で管理し、ダンジョンデータには重複して記録しない。

各探索エリアの `probability` は、基本的に合計100%となるように設定する。

---

```json
{
  "id": "ancient_ruins_02",

```

### 将来的なSQL構成

JSONからSQLへ移行する場合は、概ね以下のテーブルへ分割する。

```text
dungeons
    ↓
dungeon_stages
    ├─ dungeon_stage_entry_conditions
    ├─ dungeon_stage_clear_conditions
    └─ dungeon_stage_items
        ↓
      items
```

想定する構造は以下。

#### dungeons

```text
id
name
large_treasure_item_id
```

#### dungeon_stages

```text
id
dungeon_id
sequence
name
map_type
map_width
map_height
map_mineproberbility
map_id
```

#### dungeon_stage_entry_conditions

```text
id
stage_id
condition_type
target_id
value
```

#### dungeon_stage_clear_conditions

```text
id
stage_id
condition_type
target_id
value
```

#### dungeon_stage_items

```text
stage_id
item_id
probability
```

#### items

```text
id
name
type
sell_price
```

条件については、現時点で想定されていない種類を無理に実装せず、ゲーム内容が固まった段階で必要な条件タイプを追加する。

---

### 設計上の方針

* ダンジョン固有の設定はダンジョンデータで管理する
* アイテム固有の設定はアイテムデータで管理する
* 探索エリアの表示名と進行順を分離する
* 探索エリアごとにマップサイズを設定できるようにする
* 固定マップとランダムマップを混在可能にする
* 固定マップの実データは探索エリア設定とは分離する
* アイテムは `itemId` で参照する
* 各探索エリアのアイテム出現確率を個別に設定できるようにする
* エリア進入条件とエリアクリア条件を分離する
* 条件は `type` によって種類を識別する
* 新しい条件タイプを追加できる構造にする
* 将来的なSQL移行を考慮し、データ同士の関係をIDで管理する
* 新しいダンジョンや探索エリアを追加する際、ゲームロジック側の大幅な変更を必要としない構造を目指す

## 12. キャラクター・ビジュアル

- ドット絵を基本とする。
- キャラクターの外見カスタマイズは将来的な追加要素として検討。
- アイテム売却で得たお金の使い道の一つとして、衣装・外見変更などを追加する可能性がある。
- キャラクターを直接操作するアクションゲームにはしない。
- タイルを選択するとキャラクターが移動・採掘する形式を想定。

## 16. ゲームの中心となる体験

このゲームの中心となるのは、

> **「マインスイーパーで安全な道を推測しながら、スタミナと戦利品を天秤にかけて、どこまで潜るかを決める」**

というゲームプレイ。

さらに、

> **「失敗してもアイテムが同じ場所に残る」**

ことで、完全な損失ではなく「再挑戦」や「他プレイヤーによる救助」につながる。

リアルタイムマルチプレイを必要とせず、ソロ探索・収集・成長を中心にしながら、他プレイヤーとの緩やかなつながりを作ることを目指す。
